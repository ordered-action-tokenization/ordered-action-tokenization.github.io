Paper in one minute

Action tokenization is not just preprocessing.

VLA policies need to turn continuous robot actions into symbols before next-token training. That conversion decides whether generated sequences decode to valid actions, whether early tokens carry useful control, and whether inference must spend one VLA call per token. This paper studies action tokens under that lens.

  1. The problem: Existing action tokenizers expose a tension between compression, total decodability, AR predictability, and block compatibility. Even OAT, the ordered tokenizer this paper builds on, becomes slow when a VLA must make one sequential call per token. In knowledge-insulated VLA training, the role of action tokens is still underexplored.
  2. The method: We generalize autoregressive action-token generation into BAR, a block-wise generation method that makes the decoding schedule explicit. Starting from OAT, we compare token-wise OATsing with power-of-two OATpow2, then study how different action tokens behave in BAR and KI VLA policies.
  3. The result: ordered prefixes are easier for VLA policies to model, OATpow2 exposes a policy-call/performance trade-off under BAR, and OAT-style tokens remain useful VLM supervision even when a continuous expert controls the robot.
Small glossary

Five terms used throughout this page.

Action chunk
A short future sequence of continuous robot actions, written as \(a_{1:H_a}\in\mathbb{R}^{H_a\times D_a}\).
Action token
A discrete symbol \(T_i\in\mathcal{V}\) emitted by a next-token policy and decoded back into control.
Ordered prefix
A prefix \(T_{1:k}\) that can already decode to a complete coarse action chunk.
BAR
A block-wise autoregressive generation method that grows an action-token prefix in scheduled blocks.
KI
A VLA training setup where action tokens supervise the VLM, but a continuous expert controls the robot.
Action tokenizer desiderata

1. The tokenizer defines what the VLA has to predict.

A VLA trained with next-token prediction does not directly model continuous robot control. It models whatever token sequence the action tokenizer creates, then trusts the detokenizer to turn generated symbols back into executable actions.

continuous action chunk discrete action tokens next-token VLA target decoded control

This makes tokenization a learning problem, not just a compression problem. A tokenizer can reconstruct actions well and still be a poor VLA target if the sequence is too long, if sampled tokens fail to decode, or if the left-to-right order gives the policy no useful prediction structure.

P.1
Compact.

The token horizon should be much shorter than the raw action coordinates, without deleting control-relevant structure.

P.2
Total.

Any token string the policy samples should decode into a valid continuous action chunk, not only encoder-produced strings.

P.3
AR-friendly.

Prefixes should be meaningful, so next-token prediction becomes a structured refinement problem rather than a flat symbol stream.

BAR
Block-compatible.

Once generation is block-wise, tokens inside the same scheduled block must be jointly predictable from the realized prefix.

Ordered action tokenization

2. Ordered Action Tokenization

OAT is the ordered tokenizer this VLA paper builds on. It learns a compact discrete sequence whose prefixes can be padded, decoded, and executed as progressively refined action chunks.

Step 1
Write actions into ordered registers.

The encoder reads the whole action chunk, while causal register attention gives the latent slots a left-to-right dependency structure.

Step 2
Discretize the registers.

FSQ turns each register latent into an action token, producing a compact sequence that a next-token VLA can model.

Step 3
Train every prefix to decode.

Nested dropout masks suffix tokens during tokenizer training, forcing short prefixes to carry coarse control and later tokens to add residual detail.

For the full tokenizer story, read What's OAT; this page uses only the prefix mechanism needed for BAR and power-of-two OAT.

Prefixes become executable budgets.

A generated prefix can be mask-padded and detokenized into a complete action chunk. More tokens refine the action; fewer tokens reduce sequential policy calls.

OAT solves the representation problem.

It gives the VLA compact, decodable, ordered action tokens with meaningful prefixes.

Token-wise generation is still serial.

A length-\(K\) prefix still takes \(K\) sequential VLA calls when the policy emits one token per call.

Block-wise autoregression

3. BAR schedules autoregressive generation in blocks.

OAT makes ordered prefixes executable, but a length-\(K\) prefix still costs \(K\) sequential VLA calls. BAR targets that serial depth by introducing a schedule over prefix boundaries, unifying token-wise AR, block-wise AR, and parallel decoding.

Choose how aggressively AR is blockified.

For a 16-token action-token sequence, the schedule determines sequential VLA calls and the largest joint prediction block.

The schedule is the speed knob.

It decides how many tokens are generated per VLA call, trading serial depth against prediction difficulty.

The tokenizer has to agree.

Policy masks can group tokens at decoding time, but useful BAR needs token blocks that were trained to be predicted together.

Block-wise OAT

4. How do we blockify OAT?

BAR can group tokens at inference, but grouping is only useful if the tokenizer trained those grouped tokens as joint prediction targets. To blockify OAT, OATsing trains every prefix with a token-wise causal register mask, while OATpow2 keeps the same OAT encoder, FSQ bottleneck, prefix decoder, and nested-dropout objective, but trains power-of-two budgets with a block-causal register mask.

OATsing and OATpow2 train different dependency patterns.

BAR groups later action-token positions into one prediction step. The key question is whether the new block can be jointly predicted from the realized prefix without relying on serial dependencies inside that same block.

Flat causal chain

token-wise

Rows are query registers; columns are key registers.

Later registers can depend on all earlier registers. This matches token-wise AR, but post-hoc BAR can group tokens whose tokenizer representations were learned with serial within-block dependencies.

OATpow2

Block-causal registers

block-wise

Power-of-two blocks: [1] [2] [3-4] [5-8].

Registers attend across earlier blocks and to themselves, but not to other registers in the same block. Each block is trained for joint prediction from the realized prefix.

Prefix budgets

5. First, verify that prefixes are real action budgets.

Before training a VLA policy, we measure whether each retained prefix actually adds action information. A short prefix should already decode to a coarse action; later tokens should buy refinement rather than repeat information the prefix already carried.

\[ \hat A^{(K)} = D_\theta\!\left( T_{1:K}\oplus \langle\mathtt{MASK}\rangle_{K+1:H_l} \right), \qquad \varepsilon(K) = \mathbb{E}\!\left[ \left\lVert A-\hat A^{(K)}\right\rVert_2^2 \right]. \]

Nested dropout trains the whole prefix curve \(\varepsilon(K)\), not only the endpoint \(\varepsilon(H_l)\). OATsing learns this curve at token granularity. OATpow2 exposes the same curve at block granularity, using boundaries \(1,2,4,8,\ldots\) as successive refinement budgets.

Token cotraining

7. When tokens do not act, can they still teach the VLM?

So far, action tokens are the actions: the VLA emits them, and the tokenizer decodes them. KI asks a different question: if a continuous expert controls the robot, can action tokens still train a better VLM context?

This follows a design pattern that is becoming close to standard in modern VLA systems, including π0.5 and MolmoAct2: keep the VLM context pathway protected, and let a continuous action expert produce control. Action tokens supervise the VLM during cotraining, but a separate flow-matching expert acts at deployment. This is the knowledge-insulated cotraining setup.

The motivation is simple: flow-matching experts are strong continuous controllers, but their expert-side loss can inject noisy gradients into a pretrained VLM backbone and damage the semantic knowledge that made the backbone useful. KI blocks that path. Token cross-entropy adapts the VLM toward motor-relevant context; flow matching trains the action expert; stop-gradient keeps the expert loss from rewriting the VLM.

The cotraining objective has two paths.

The action-token branch gives the VLM an action-aware cross-entropy signal. In parallel, the action expert learns a continuous flow-matching controller conditioned on detached layer-wise K/V values from the image, language, and robot-state prefill. The flow loss treats those K/V values as constants and updates only the expert side of the model.

\[ \mathcal{L}_{\mathrm{KI}} = \mathcal{L}_{\mathrm{tok}}(T_{1:H_l}\mid c) + \lambda\, \mathcal{L}_{\mathrm{flow}} \!\left( a_{1:H_a}, \tilde a_{1:H_a}^{\,\tau}, \tau; \operatorname{sg}(\mathrm{KV}_{\mathrm{VLM}}(c)) \right). \]

\(\operatorname{sg}(\cdot)\) is stop-gradient. The token loss updates the VLM context pathway; the flow loss updates the continuous action expert using detached context K/V values, not K/V values from teacher-forced action-token positions.

At inference, the token branch is removed.

At deployment, the VLM is prefilled once on image, language, and robot-state context. Its logits are ignored, no action-token decoding loop is run, and the controller keeps only the detached K/V cache. The continuous action expert then iteratively denoises an action chunk from that fixed context.

KI experiments

8. In KI, action tokens still matter.

The KI setting removes action-token decoding from deployment, but it does not make the tokenizer irrelevant. Different action tokens still train different VLM context representations, and those differences show up in closed-loop control.
